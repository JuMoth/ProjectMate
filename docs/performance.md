# 성능 개선 기록

## 개발 기록 1. 프로젝트 API 응답 시간 측정 및 HTTP 캐시 동작 확인

## 1. 문제 상황
- 프로젝트 목록 및 상세 조회 API의 응답 속도를 확인하고자 했다.
- 실제 API 요청이 어느 정도의 시간 안에 처리되는지 측정할 필요가 있었다.
- 프로젝트 참여 신청 기능 개발 과정에서 새로고침 후 API 요청의 HTTP 상태 코드가 200 OK 또는 304 Not Modified로 표시되는 현상을 확인했다.

## 2. 원인 분석
- Chrome 개발자 도구의 Network 탭을 이용해 API 요청의 Duration을 측정했다.
- 측정 대상:
  - `GET /api/projects`
  - `GET /api/projects/1`
- 각 API를 2회씩 요청하여 응답 시간을 확인했다.
- HTTP 304 Not Modified는 서버에서 리소스가 변경되지 않았음을 알려 브라우저가 기존 캐시를 재사용하도록 하는 응답이다.
- HTTP 200 OK는 요청이 정상 처리되어 서버가 응답을 전달했음을 의미한다.

## 3. 해결 방법
- 어떤 개선 방법을 시도했는가?
  - Chrome 개발자 도구 Network 탭에서 API 요청 시간을 측정했다.
  - 새로고침 과정에서 발생하는 HTTP 상태 코드의 차이를 확인했다.
  - Network 탭의 Disable cache 옵션을 통해 캐시 사용 여부를 확인할 수 있음을 파악했다.

- 최종적으로 어떤 방법을 선택했는가?
  - 기존 API 응답 시간을 기준값으로 기록했다.
  - HTTP 304와 200의 차이를 이해하고 정상적인 브라우저 캐시 동작으로 판단했다.
  - 실제 성능 개선 작업은 진행하지 않았으므로 별도의 개선 코드는 적용하지 않았다.

## 4. 개선 결과
- 개선 전 측정값:
  - `GET /api/projects`: 6ms, 4ms
  - `GET /api/projects/1`: 7ms, 9ms

- 개선 후 측정값:
  - 별도의 성능 개선 작업을 진행하지 않아 측정하지 않음.
  - 기존 측정 결과 기준:
    - 프로젝트 목록 API 평균 응답 시간: 5ms
    - 프로젝트 상세 API 평균 응답 시간: 8ms

- 측정 환경 및 조건:
  - Chrome 개발자 도구 Network 탭
  - Fetch/XHR 요청의 Duration 기준
  - 각 API를 2회씩 측정
  - 로컬 개발 환경에서 측정

- 확인 방법:
  - Network 탭에서 API 요청의 Duration 항목 확인
  - HTTP Status Code 확인
  - 새로고침 후 200 OK 및 304 Not Modified 응답 확인
  - Disable cache 옵션을 이용한 캐시 동작 확인 방법 파악

## 5. 배운 점
- Network 탭을 활용하면 실제 API 요청의 응답 시간을 확인할 수 있다는 점을 배웠다.
- 성능 개선을 주장하려면 개선 전후의 측정값과 동일한 측정 조건이 필요하다는 점을 이해했다.
- HTTP 304 Not Modified는 오류가 아니라 브라우저 캐시 재검증 과정에서 발생할 수 있다는 점을 알게 되었다.
- HTTP 상태 코드만으로 성능을 판단하기보다 실제 요청 시간과 응답 데이터를 함께 확인해야 한다는 점을 배웠다.
